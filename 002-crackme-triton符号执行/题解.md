**最终密码：** `52pojie666`

## 1. 摘要

本次任务的目标不是简单让程序显示成功提示，而是分析一个 32 位 Windows Crackme，恢复它真正接受的密码，并在原始程序中完成验证。

最终通过静态分析、字符串解码、动态观察、函数级模拟、Ghidra 反编译和原始 x86 机器码符号执行，恢复出密码：

> `52pojie666`

该密码不是通过修改跳转、篡改返回值或制作强制成功版程序得到的。最终结果来自原始二进制中的校验函数、目标常量表和 32 个同构混合函数。独立重算得到：

- 修改后的 FNV-1a 指纹：`0x2D9CBA87`
- 二级自定义哈希：`0x325340CA`
- 加载器/映像比较派生值：`0xF5374791`
- 密码长度：10 字节

用户随后在未修改的 `crackme.exe` 中输入该密码，确认结果完全正确。

### 1.1 密码到底是怎么恢复出来的（通俗版）

可以把这个 Crackme 想象成有 **32 把锁**，而程序里同时保存了每把锁对应的正确结果。

每把锁并不会检查完整密码。编号为 `i` 的锁主要查看：

```text
密码[i mod 密码长度]
```

也就是密码中的某一个字符。不过，为了不让人直接逐字符读取，它还把这个字符与整串密码的两个哈希值、文件映像校验值以及一批不同的乘法和旋转常量混在一起。

恢复过程可以简化为：

```text
原始密码
   ├─> 整串 FNV 指纹 ─────────────┐
   ├─> 整串二级哈希 ──────────────┤
   └─> 第 i 个字符 ─> 第 i 个函数 ├─> 必须等于第 i 行正确答案
文件映像校验值 ───────────────────┘

对 i = 0 ... 31 全部成立
```

首先，从 32 行正确答案中逆运算出了一个共同的整串 FNV 指纹：`0x2D9CBA87`。32 行得到的结果完全相同，说明这些表项确实描述的是同一个正确密码。

然后把“密码长度、每个密码字符、二级哈希、映像校验值”当作未知数，让 Triton 直接执行原文件中的 32 个 x86 函数，并要求：

```text
第 0 个函数输出 = 表中第 0 行
第 1 个函数输出 = 表中第 1 行
...
第 31 个函数输出 = 表中第 31 行
```

这相当于把 32 个二进制方程联立起来。对程序允许的密码长度逐一检查后，只有长度 10 能同时满足全部方程，并且所有字符都是可打印 ASCII：

```text
52pojie666
```

最后再用另一套独立代码重算整串密码的两个哈希，分别得到 `0x2D9CBA87` 和 `0x325340CA`，与二进制目标完全一致。用户在原始程序中输入后也验证成功。因此这不是猜测密码，也不是修改程序绕过验证，而是从 32 个校验函数和正确答案表联立恢复出来的。

## 2. 授权、边界与原则

开始前先确认了是否允许直接运行未知可执行文件。用户明确允许后，分析遵循以下边界：

1. 目标限定为当前目录中的 `crackme.exe`。
2. 下载或安装的工具主体必须位于当前工作目录。
3. 原始文件应尽量保持不变，先静态分析，再进行动态执行。
4. 每次重要尝试都记录到 `crackme_decryption_log.md`。
5. 最终成功标准是原程序出现正确结果，而不是单纯找到可疑字符串或制作补丁版。

后来用户进一步明确要求采用反编译、二进制查找等“破解”方式，不接受强制成功。此要求成为后半程路线选择的决定性约束。

## 4. 第一阶段：静态侦察

### 4.1 文件占用与权限问题

首次使用十六进制读取时，系统报告文件正被另一进程占用。没有贸然结束进程，而是继续尝试只读操作。哈希计算随后成功，说明占用可能来自短暂的扫描行为。

尝试通过 WMI 查询占用进程路径时遇到“拒绝访问”。这一步没有继续提权或终止系统进程，而是记录异常并转向不依赖 WMI 的分析方法。

### 4.2 字符串中的诱饵

普通 ASCII 字符串扫描发现多条看似有价值的信息：

- `success: password verified`
- `serial validation success`
- `authentication success token`
- `password_success=true`
- `access granted: success`

但目标提示 `Password correct!` 并未以明文出现。这些字符串也没有直接形成成功路径的有效交叉引用，因此被视为诱饵或干扰数据，而没有据此猜测密码。

### 4.3 异常重定位区

`objdump` 在解析 `.reloc` 时，第一段数据较正常，后续却出现类似随机重定位条目的内容。这说明程序可能把普通数据伪装在重定位区域，或故意制造反分析噪声。结论是不能盲信节名称，需要结合代码访问行为判断数据含义。

## 5. 界面和字符串解码

通过反汇编定位到 `0x00401200` 的字符串解码函数。其核心关系可以表示为：

```text
plain[i] = cipher[i] XOR ((i × (3i + 29) + key) mod 256)
```

解码后的字节被扩展为 UTF-16，用于 Windows 宽字符界面 API。由此恢复出：

- 窗口类：`CkWnd_8741`
- 窗口标题：`CrackMebyBS`
- 输入控件类：`Edit`
- 按钮类：`Button`
- 按钮文本：`Verify`
- 消息框标题：`Result`

### 5.1 一次错误判断

最初尝试把 `0x4047DC` 和 `0x4047F0` 的字节数组直接按固定密钥解码，输出出现不可编码字符并失败。重新检查调用链后发现，这两段不是可直接解码的完整字符串，而是根据校验结果用掩码选出的中间密文，最终解码密钥也来自运行时状态。

因此修改了 `analyze_crackme.py`：保留对确定性界面字符串的解码，只把这两段数据输出为十六进制，不再误报成明文。

## 6. 第一次动态执行

程序窗口成功启动后，观察到：

- 输入框控件 ID：`1001`
- Verify 按钮 ID：`1002`

首次动态尝试使用空密码，目的不是猜解，而是确认失败路径、界面行为和消息解码是否正确。结果弹出：

> `Password incorrect.`

这个结果验证了三点：

1. 找到的窗口过程和按钮消息处理正确。
2. 密码读取路径确实位于当前分析的函数链中。
3. 真实提示信息是在运行时生成的，不是字符串扫描得到的诱饵。

动态操作中也遇到过控件可访问性索引没有几何信息的问题。处理方式是重新获取窗口截图和焦点状态，再使用当前截图中的按钮坐标完成单次点击，没有复用过期坐标。

## 7. 定位核心验证链

窗口过程位于 `0x00403930` 附近。点击 Verify 后，程序执行以下流程：

1. 从编辑框读取最多 63 个 Unicode 字符。
2. 确认所有字符都在 ASCII 范围内。
3. 转换为单字节密码缓冲区。
4. 调用 `0x004036C0` 计算映像完整性/加载器派生值。
5. 调用主验证器 `0x00402140`，输出 20 字节结果，即 5 个 32 位字段。
6. 调用 `0x00401F00` 将输出字段和内置表比较，并生成正确或错误消息。

成功判定使用的四张表分别位于：

- `0x00404320`
- `0x004043A0`
- `0x00404420`
- `0x004044A0`

第一个输出字段作为 0 至 31 的表索引，其余四个字段必须与该行四个目标值完全一致。完整性参数还必须等于：

```text
0xDE2F567F
```

## 8. 函数级模拟与第一条求解路线

为了避免反复启动 GUI，建立了 `emulate_validator.py`：

- 使用 Unicorn 加载原始 PE 映像。
- 只执行 `0x00402140` 验证函数。
- 为计时、进程 ID、内存映射和虚拟内存 API 提供本地桩。
- 不修改原始文件，不执行整个 GUI 程序。

模拟器成功对空密码和多个测试字符串生成稳定的五字段输出。这证明验证函数可以在受控环境中独立运行。

随后从成功判定反推出目标表行需要的修改后 FNV-1a 指纹：

```text
0x2D9CBA87
```

`solve_password.py` 使用 Z3 建模两类哈希：

1. 修改后的 FNV-1a。
2. 一个包含旋转、乘法、异或和累加的自定义二级哈希。

结果是长度 1 至 7 在初始常见字符集内可以证明无解，但长度 8 以上因为位向量乘法和旋转组合复杂，求解器多次返回 `unknown` 或超时。

### 8.1 对模型的优化

FNV 乘数 `0x01000193` 在模 `2^32` 环中可逆，因此把最后一个字符从独立变量改为根据目标哈希和前缀反推，以减少一个变量。优化后求解有所改善，但仍未有效突破较长密码。

这条路线提供了正确的全局指纹，却不适合单独恢复完整密码，因此需要改变方法。

这是整个分析中最重要的路线调整：目标从“让程序成功”重新收紧为“从二进制恢复真实口令”。

## 10. Ghidra 反编译

本机没有现成反编译器，但有 Java 17，因此下载了便携版 Ghidra 10.4，并解压到工作目录的 `.tools\ghidra`。使用无界面模式导入原文件，通过自定义脚本 `ghidra_scripts\ExportCrackme.java` 导出关键函数伪代码到 `ghidra_decompiled.c`。

### 10.1 工具和环境问题

Ghidra 下载首次在工具调用的两分钟上限处超时，但后台下载进程仍在继续。通过持续检查文件大小发现 ZIP 从约 159 MB 增长到最终的 370,096,003 字节，因此没有重复下载或破坏文件，而是等待其自然完成。

第一次无界面分析因工程父目录不存在而失败。创建目录后重试，又遇到 PowerShell 环境变量被外层解析的问题，导致原计划的用户目录重定向没有完全生效。最终分析成功，但 Ghidra 运行时仍使用了默认用户缓存路径。便携程序、工程脚本和导出结果均位于工作目录；该问题被记录为工具运行缓存行为，而不是系统安装。

### 10.2 关键结构发现

Ghidra 反编译显示，验证器包含 32 个同构函数。第 `i` 个函数读取：

```text
password[i mod length]
```

并把该字符与以下共享上下文混合：

- 密码长度
- 完整性参数 `0xDE2F567F`
- 修改后的 FNV-1a 哈希
- 自定义二级哈希
- 加载器/映像比较派生值
- 另一个由固定异或关系产生的上下文字段

每个函数拥有不同的旋转位数、乘数、加数和字符乘数，但整体结构相同。其返回值依次与 `0x00404320` 表中的 32 个目标值比较。

更重要的是，对 32 行目标表逆运算后，每一行都导向同一个 FNV 指纹：

```text
0x2D9CBA87
```

32 行全部一致，证明目标表不是无关噪声，而是在不同混合函数下描述同一个正确密码。

## 11. 原始机器码符号执行

为了避免手工抄录 32 个长表达式时出错，最终采用 Triton 对原始 x86 指令做符号执行。脚本为 `recover_password_binary.py`。

### 11.1 符号变量

每个候选长度下，设置以下符号变量：

- 密码的每一个可打印 ASCII 字节
- 自定义二级哈希值
- 加载器/映像比较派生值

其余已经从二进制证明的字段固定为真实常量，例如 FNV 指纹和完整性参数。

### 11.2 约束建立

对全部 32 个真实函数逐个执行原始机器码，并加入约束：

```text
function_i(context, password[i mod length]) == target_table[i]
```

同时将密码字符限制在可打印 ASCII 范围。此方法没有枚举整个字符串，也没有使用人工改写的等价函数；它直接让二进制指令语义参与求解。

### 11.3 调试中的模型错误

初版脚本有两类错误：

1. 一度把目标表地址误写成 `0x004043A0`，而当前求解的实际输出字段应对应 `0x00404320`。
2. 把加载器派生上下文字段凭模拟环境固定为 `0`，后来又尝试固定为 `1`，均导致所有长度无解。

问题的根源是模拟器中的 API 桩和真实映像加载行为不同，不能把模拟环境观察值直接当作原程序常量。

最终改变模型：把加载器派生值本身也设为符号变量，让 32 个真实函数和目标表共同反推它。这一调整立即得到唯一可打印解。

## 15. 方法论总结

### 15.1 不要相信孤立字符串

Crackme 中经常放置看似明显的成功、序列号或认证文本。是否有价值必须由代码引用和控制流证明，而不是只看 `strings` 输出。

### 15.2 静态和动态分析应互相校验

静态分析定位了窗口过程、输入控件和校验函数；空密码动态测试确认了失败路径和消息生成机制。两者结合比单独依赖任一方法更可靠。

### 15.3 模拟环境的数据不能无条件等同于真实环境

函数级模拟非常适合观察结构，但 API 桩、映像地址和重定位行为可能改变某些派生值。本次最关键的误区就是把模拟器里的上下文字段固定到真实求解模型中。

### 15.4 优先利用重复结构

32 个同构函数是本题最有价值的设计线索。单个函数很难同时恢复多个未知量，但 32 行使用共享上下文、不同字符索引和不同常量，形成了一个高度超定的约束系统，足以直接恢复密码。

### 15.5 区分“破解密码”和“绕过验证”

修改跳转、返回值或输出结构可以让程序显示成功，但不等于找到了真实密码。本次在用户明确要求后放弃了绕过路线，最终结果来自原始二进制约束，并由原程序验证。
